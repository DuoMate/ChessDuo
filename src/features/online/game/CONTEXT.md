# Module: Online Game (Multiplayer)

## Purpose
Real-time multiplayer 2v2 game implementation using Supabase Broadcast + Presence for communication.

## Key Files
| File | Purpose |
|------|---------|
| `onlineGame.ts` | OnlineGame class — implements GameInterface, manages Supabase channels, turn coordination |

## Logic & Decisions
- Implements `GameInterface` — same contract as LocalGame.
- Uses Supabase `RealtimeChannel` for move/lock/resolution payloads.
- Coordinator pattern: one player per turn resolves moves (not a central server).
- Channel lifecycle managed via `subscriptionManager`.
- Move flow: select → `broadcastMove()` → `broadcastLocked()` → coordinator resolves → `broadcastResolution()`.
- Handles reconnection: syncs state from DB on reconnect.
- OnlineGame-specific methods (not on GameInterface): `joinRoom()`, `broadcastMove()`, `broadcastLocked()`, `isCoordinator()`, `waitForTeammateLock()`.

## Dependencies
- `GameState` from `game-engine/`, `GameInterface` from `shared/`
- `@supabase/supabase-js` for real-time channels
- `lib/gamePersistence` for save/load, `lib/subscriptionManager` for channel tracking

## Recent Changes
- **2026-08-23**: **P0 — "Move submission failed" 403: turn_submissions had no UPDATE policy for idempotent re-submission.** Root cause proven by local PG16 RLS reproduction: `submitMoveToDB` submits via PostgREST UPSERT (`Prefer: resolution=merge-duplicates` → `INSERT … ON CONFLICT (game_id,turn_number,player_id) DO UPDATE`), and PostgreSQL authorizes the conflicting-row branch under the table's UPDATE policy — which `supabase.sql` never defined (SELECT + INSERT only). Every legitimate re-submission of an already-persisted move (retry after lost response, resubmit after refresh) failed with 42501 → HTTP 403 → toast + rollback, and the turn could never resolve. Fixes: (1) DB — new least-privilege policy `"Players can update their own moves"` on `turn_submissions` (`auth.uid() = player_id`, room membership via `is_room_member`, WITH CHECK keeps `player_id` immutable; no DELETE policy); see `supabase/migrations/2026-08-23_turn_submissions_update_policy.sql` and the updated `supabase.sql` + `rlsSecurity.test.ts` inventory. (2) FE — `submitMoveToDB` now performs an authoritative read-back (`readOwnSubmission`) when an upsert errors or throws: a row holding THIS exact move counts as idempotent success (`SUBMIT_ALREADY_PERSISTED` trace), anything else still fails visibly with full rollback — a rejected write is never disguised as success. Verified empirically post-migration: own-row re-submit allowed; cross-player / non-member / anon / player_id-rewrite all denied. Tests: `onlineGameSubmission.test.ts` (RLS-403 regression trio).
- **2026-08-23**: **ADR-006 — Idempotent Resolution & Divergence Policy (root cause fix for "Invalid move: Nf6").** The throw was evidence of client/authoritative position divergence: a missed `turn_resolved` left a client's board a move behind while `handleTimerSync`/turn-number syncs advanced `_currentTurnNumber` anyway, so next-turn submissions were accepted against a stale board and `gameState.resolve()` threw at `chess.move()`. Fixes: (1) `resolvePendingMoves` probes both pending SAN moves against the turn-start FEN via `isMoveLegalAt` BEFORE evaluation — any illegal move triggers `_recoverFromDivergence` (discard turn, re-sync from DB, reopen submissions) and throws typed `STATE_DIVERGENCE`; (2) single-writer guard throws `RESOLVE_IN_PROGRESS` on concurrent entry; (3) `handleTurnResolved` dedupes equal-seq duplicates via new `_lastAppliedResolution {seq, winningMove}` and replaces the blind `board.move()` fallback with a validated direct-apply / divergence-re-sync split; (4) `handleTimerSync` no longer mutates turn numbers; (5) `syncGameState` stale-authority guard refuses to roll the board back onto a games row with shorter move history. `[RESOLVE][FORENSIC]` dev-gated snapshots log FEN/legality/pending state before every mutation. Tests: `onlineGameDivergence.test.ts`. See ADR-006 in `docs/ARCHITECTURE.md`.
- **2026-08-19**: **P1 — move-resolved display collapsed both submissions.** `resolvePendingMoves()`'s move-pair selection was order-dependent over the pending-moves `Map`: when the teammate's entry was iterated before the coordinator's own entry, the coordinator branch overwrote `move1` and never promoted the teammate to `move2`, so both submissions collapsed to the coordinator's move (`isSync === true`, both accuracy values equal). Replaced the loop with an order-independent selection (coordinator's own entry = `move1`, first other entry = `move2`; bot-team fallback unchanged). The evaluation/scoring path is untouched — it now simply receives the two distinct submissions. Tests: `onlineGameDuoCycle.test.ts` (teammate-moves-first + reverse-winner cases).
- **2026-08-18**: **P0 — Duo lobby timeout + board freeze after shadow move.** (1) The fallback poll no longer stops on the non-coordinator once it counts 2 humans — it keeps re-checking the authoritative `games` row until `PLAYING`/`GAME_OVER`, so a missed `game_started` broadcast can no longer strand the joiner in the lobby until the 60s timer. `syncGameState()` now returns whether a saved game was applied and never swallows failures (callers can retry). `saveGameState` failures propagate (see `gamePersistence.ts`), and the game-start read-back of `_gameId` is retried 5× so a slow read can't silently degrade submissions to broadcasts. (2) Move-state machine recovery: `submitMoveToDB` returns a boolean and on DB failure fully rolls back (clears the local pending move/lock, resets `turnState` to `'selecting'`, notifies, best-effort broadcasts `player_move`) so the board is never permanently disabled; `waitForTeammateLock` timeout re-fetches the current turn's submissions from the authoritative DB (`restoreCurrentTurnSubmissions`) so a missed postgres_changes INSERT still resolves; `waitForTurnChange` timeout triggers `syncGameState()` instead of doing nothing. `_finishResolution` no longer aborts the in-session resolution when persistence fails. `GameState` gains `clearPendingMove(player)`. New `[DUO:ROOM]`/`[DUO:GAME]`/`[DUO:REALTIME]`/`[DUO:MOVE]`/`[DUO:CLOCK]` dev-gated structured diagnostics via `duoGameTrace.ts` (hashed user id; no secrets). Tests: `onlineGameLobbyRecovery.test.ts`, `onlineGameFreezeRecovery.test.ts`.
- **2026-08-17**: **`startGameWhenReady()` readiness is now DB-authoritative.** The start gate previously required `presenceRoster.size >= requiredHumans` (realtime presence as the sole source of truth), which left both players in the lobby to time out whenever presence metadata did not reach 2 (e.g. a joiner whose presence lagged). Local PG16 reproduction proved the hardened RLS does not block any member game-start op. Fix: the merged roster (`room_players` authoritative + presence backfill) is computed first and gates readiness (`allHumans.length >= requiredHumans`); the "every human present" guard was removed because the atomic `join_room_by_code` RPC guarantees committed membership before a client enters `/game` (the joiner syncs via the `game_started` broadcast). The fallback poll now triggers only the authoritative DB coordinator (alphabetically-first non-bot member) instead of the first *present* player, and `startGameWhenReady` also rejects non-coordinators, preventing double-start when presence shows only self.
- **2026-08-17**: **`joinRoom()` uses the atomic join RPC.** Replaced the direct `room_players` upsert (and removed the raw-fetch diagnostic fallback) with `joinRoomByCode(room.code)`. The RPC returns the authoritative team; `this._team` adopts it (with a presence re-track if it differs) and presence `track()` now uses `this._team`. Registration failure is non-fatal (membership is established upstream via the RPC; presence carries the team). See `src/lib/CONTEXT.md` and `supabase/migrations/join_room_by_code.sql`.
- **2026-08-17**: **P0 fix — Duo lobby timeout on entry.** `startGameWhenReady()` only counted humans from the `room_players` SELECT, so when the joiner (2nd account, opened the invite link) was already present in the realtime channel but their upserted row wasn't committed/visible yet, the human-count guard deferred and never recovered: fast-retries (12×250ms) + the 15s fallback-poll budget expired while the 60s lobby timed out. Now the human count is **presence-authoritative**: the roster merges channel presence (player_id + team, with `room.host_team` fallback for a metadata-less joiner) with `room_players`, presence is the minimum-humans gate, and unknown-team humans are backfilled from presence/host_team. The coordinator also re-broadcasts `game_started` on every presence sync/join once PLAYING (lost-early-broadcast self-heal), and the fallback poll budget was extended 15s→55s to cover the full lobby window.
- **2026-08-17**: **P0 fix — black-side bot freeze in Duo mode.** `resolvePendingMoves()` hardcoded WHITE = human team / BLACK = bot team: the WHITE branch only picked `move1` when `player === this._playerId` (the coordinator's own UUID), so when the Duo host picks BLACK (humans on BLACK, bots on WHITE via `bot_teammate_*`), the White bot's first turn threw `'Both pending moves must be set'` and the initial-bot trigger caught it without retry → game froze. Made move-pair selection color-agnostic: coordinator's own move is `move1` when present, otherwise any two submitted moves are used. Same architecture for both colors; no new bot path.
- **2026-08-12**: **P0 fix — Duo turn-resolution failure.** `syncGameState()` did not call `gameState.startMatch()` when `needsReplay` was false (normal first-join path), leaving `GameState._phase` at `WAITING`. All `setPendingMove` calls were silently dropped by the phase guard (`gameState.ts:140`), preventing shadow-move display, resolution, turn advancement, and forward/backward navigation. Fix: added `if (phase === WAITING) startMatch()` after the `needsReplay` else-branch, before `startPendingTurn()`.
